## Existing System

Today a reader who wants to check a suspicious message has three options, and each one covers only part of the problem.

**Manual fact-checking websites.** Sites such as BOOM, Alt News, Factly and the PIB Fact Check unit publish articles that debunk specific viral claims. Their verdicts are reliable and come with sources, but each article covers one claim, takes hours or days to publish, and only exists for claims that became popular enough to be noticed. A reader must search for the claim and hope it has been checked.

**Fake news classifiers.** Research systems and some browser extensions classify an article as fake or real with a trained model. They answer instantly, but they give one label for the whole article, they are trained almost entirely on English, and they do not explain the label. As Chapter 5 shows, much of their accuracy comes from recognising the writing style of the sources in the training data.

**Image checks.** Reverse image search finds earlier copies of a photograph, which exposes old photos reused out of context, but it cannot say whether a new image was generated by a model. Separate AI-image detectors exist, but they are not connected to text checking.

### Disadvantages of the existing system

- Verdicts are given for the whole article. The reader is not told which sentence is false.
- Classifiers do not explain their output, so a wrong verdict cannot be spotted.
- Retrieval tools that rank evidence by similarity cannot tell supporting evidence from contradicting evidence.
- Support for Telugu is limited to manual fact-check articles.
- Text and images are checked with different tools.
- Checking a list of messages means checking each one by hand.

## Proposed System

TruthLens AI combines classification, explanation and claim-level evidence checking for English and Telugu text, and AI-generated image detection, in one web application.

For text, the article goes through two paths at once. The classifier path (DeBERTa-v3-large for English, IndicBERT v2 for Telugu) gives a fake probability, and LIME marks the words that pushed it. The verification path splits the article into claims, retrieves evidence for each one, and uses an NLI model to label each claim Support, Contradiction or Unknown. The two paths are fused into one fake risk, and the report shows the verdict, the highlighted article, the claims with their status, and the evidence behind each claim.

For images, a linear classifier on CLIP ViT-L/14 features says whether the image is a real photograph or AI-generated, and a Grad-CAM heatmap shows the regions that drove the decision.

Batch mode runs the same checks on a CSV file of texts or a set of images and returns a CSV of results. Every check is saved in a local history.

### Advantages of the proposed system

- Each claim in an article gets its own status and evidence, so the reader knows what exactly is false.
- Contradicting evidence is detected explicitly through NLI, not inferred from similarity.
- Every verdict has an explanation: highlighted words for text, a heatmap for images.
- English and Telugu are handled in one interface, with automatic language detection.
- Text and images are checked in the same tool.
- Batch mode handles hundreds of items with one upload.
- All models are free and open. The system runs offline on a laptop once the models are downloaded.
- One command installs and starts the system on Windows, Linux or macOS.

## Feasibility Study

### Technical feasibility

Every component uses mature, open-source software. The models are available on Hugging Face under licences that allow academic use: MIT for DeBERTa-v3, IndicBERT v2, BGE-M3 and the NLI models, Apache 2.0 for BERT-base, OpenAI's MIT release for CLIP, and CC BY-NC 4.0 (non-commercial) for NLLB-200. PyTorch [38] and the Hugging Face Transformers library [33] load and fine-tune them with a few lines of code. Training DeBERTa-v3-large needs a GPU with about 16 GB of memory, which the free T4 in Google Colab and Kaggle provides; the notebook's full training run is planned to fit in one free session of 3.5 to 4.5 hours. Inference runs on a CPU, slowly for the largest model but within the limits of a demonstration. The project is technically feasible.

### Economic feasibility

The project costs nothing beyond the students' existing laptops. All datasets download without payment or an account, all models are free, training uses free cloud GPUs, and the software stack (Python, FastAPI, React, SQLite) is open source. The optional Google Fact Check Tools API is free within its quota. The project is economically feasible.

### Operational feasibility

The user interface needs no training: the Start page has one text box and one image drop area, and every report uses plain words such as "Likely fake" and "Contradicted". The launcher creates the Python environment, installs the packages, starts both servers and opens the browser, so the students and examiners do not need to know Python or Node.js to run it. The project is operationally feasible.

### Functional requirements

TABLE: Functional requirements
| ID | Requirement |
|---|---|
| FR1 | The system shall accept news text of 10 to 20,000 characters in English or Telugu. |
| FR2 | The system shall detect the language automatically and allow the user to override it. |
| FR3 | The system shall classify text as Fake or Real with a confidence value. |
| FR4 | The system shall highlight the words that most influenced the text verdict. |
| FR5 | The system shall extract up to eight check-worthy claims from an article. |
| FR6 | The system shall retrieve evidence for each claim and label it Support, Contradiction or Unknown. |
| FR7 | The system shall show the evidence passage, its source and NLI scores for each claim. |
| FR8 | The system shall combine claim labels into a credibility score and overall verdict. |
| FR9 | The system shall fuse the classifier and claim results into one fake risk. |
| FR10 | The system shall accept JPG, PNG and WEBP images up to 15 MB and classify them as Real or AI-generated. |
| FR11 | The system shall produce a Grad-CAM heatmap for each image verdict. |
| FR12 | The system shall check a CSV file of texts or a set or ZIP of images in one request. |
| FR13 | The system shall let the user download batch results as a CSV file. |
| FR14 | The system shall store every check in a history that can be viewed, filtered and deleted. |
| FR15 | The system shall show whether each model is trained and loaded. |
| FR16 | The system shall let the user save any report as a PDF. |

## Software Development Model

The project followed an iterative model. A first version with all three pipelines and a basic interface was built and tested end to end with tiny placeholder models. The training notebook was then developed and run in a quick-test mode that trains every model on a few hundred examples in about 25 minutes, which caught problems such as the WELFake label inversion before the full run. The interface was redesigned twice after review. Each iteration ended with the application running and the test cases in Chapter 7 passing.
